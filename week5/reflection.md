# Lab 5 Reflection: SELECT Safety & Debugging

`SELECT` statements are part of DQL(Data Query Language) and only read data from tables. Because they don't change any underlying records or alter table structures, running them is completely safe when exploring a database. There is no danger of accidentally modifying or deleting anything. On the other hand, DDL statements like `CREATE` or `DROP` change the schema, while DML statements like `INSERT`, `UPDATE`, and `DELETE` alter or wipe out the actual data. Running DDL or DML without double-checking can easily corrupt a database or permanently erase records.

For Task 4, I tested a value mismatch by changing `WHERE species = 'Cat'` to `WHERE species = 'Feline'`. The original query displayed all the cat records, but the modified version returned an empty set (0 rows) without giving any syntax error. I diagnosed what happened by checking the data inside the `pet` table using `SELECT * FROM pet`. Since all cat entries were stored under the string `'Cat'` rather than `'Feline'`, the condition evaluated to false for every row. Checking the raw table data helped me catch that it wasn't a syntax issue, but simply a logic mismatch between my query filter and the stored text values.
